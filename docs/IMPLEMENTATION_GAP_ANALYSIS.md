# V1 未实现功能原因梳理

日期：2026-10-15

本文件回答一个问题：为什么设计稿里已经出现了很多入口，但对应业务仍显示“待实现”。结论先行：当前不是所有功能都没有做，而是 **Phase 1–3 的基础运行、姿势状态、提醒链路、Phase 4A 的症状记录基础、Phase 4B 的专业确认训练基础（含候选资料包导入）、Phase 4C–4D 的统计与交互收口，以及 Phase 5 的可靠性基础已完成；真实 Windows 验收和 Phase 6 安装交付仍未完成**。页面先补齐，是为了让产品结构完整，不把占位页冒充为可用功能。

## 二、为什么没有直接把占位按钮做成可用

### 1. 页面和业务数据不是同一件事

当前 SQLite schema 版本 6，已包含：

- `app_settings`
- `posture_events`
- `posture_snapshot`
- `environment_events`
- `reminder_deliveries`
- `symptom_entries`
- `exercises`
- `exercise_plans`
- `exercise_logs`

不新增备份记录表：备份是用户选择路径的 SQLite 一致性快照，恢复前执行完整性和 schema 校验。统计不新增读取模型表，而是从既有姿势事件和症状记录只读推导；训练资料已经有正式数据契约，但没有内置任何真实动作资料。按照 PRD“不得伪造记录、统计”的要求，统计页只绘制本地已保存事实，缺失值保持为空，不使用演示数据。

### 2. 症状功能缺少完整契约，不只是几个输入框

F06 的统计契约已在 Phase 4C 实现并测试；仍需专业人员复核规则文案和后续医学产品边界：

- 每日记录的唯一性和可编辑规则；
- 疼痛 `NULL` 与 `0` 的存储和显示区别；
- 本地日期、UTC 时间、跨午夜的归属规则；
- 部位、腿部症状、活动关系的枚举或自由文本边界；
- 保存失败时的事务和界面反馈；
- CSV 导出范围、确认和隐私提示；
- 统计展示不应被解释为病情判断或医学趋势结论；
- 与异常症状提示共用的字段契约。

以上数据契约已在 Phase 4A / 4C 冻结并接入症状与统计 UI；医学文案复核和真实目标机验收仍不属于本阶段，数据备份 / 恢复已在 Phase 4D 接入。

### 3. 康复训练不能用示例动作填充真实功能

PRD 明确要求：动作必须记录来源、内容、禁忌、审核人、专业确认时间和状态；未经专业确认不得加入执行计划；初始可执行计划必须为空。

当前没有医生或康复治疗师确认的内置动作资料，也没有可验证的专业资质系统。因此页面中的“猫牛式、桥式、腰部拉伸”仍只能作为设计稿位置占位；用户可以录入自己已有的专业资料，但程序只记录用户填写的确认信息，不验证资质，也不会自动推荐或排程。这个边界需要专业内容和数据契约，不是单纯开发一个按钮。

### 4. 异常症状提示必须先有医学复核后的规则和文案

PRD 要求使用固定、可测试的规则，不使用 LLM 推理，也不能把提示写成诊断结论。当前仍未完成：

- 警示字段和选项的专业复核；
- 会阴 / 肛周麻木、排尿排便改变、进行性腿无力等文案的专业复核；
- 就医紧迫性和“停止训练”的文案审查；
- 规则单元测试和误触发测试。

当前实现只执行固定规则并显示非诊断性提示，不推荐训练，也不替代医疗评估；发行前仍需完成专业复核和真实目标机验收。

### 5. 恢复功能不能只靠启动时重新开始计时

当前 `PostureService` 使用事件日志和快照恢复，并在发现上次运行未正常结束时进入待核实状态。这解决了“不要静默清零”的基础问题，但距离 F09 完整交付还差：

- 锁屏、睡眠、唤醒之间的真实 Windows 事件验收；
- 系统时间跳变和跨时区处理；
- 用户确认“中间一直坐着 / 中间起身 / 无法判断”的完整 UI；
- 用户追述时间的精度和证据标记；
- SQLite 完整性检查、备份、恢复和损坏处理；
- 崩溃、断电和重复启动故障注入。

恢复场景宁可保留“未知 / 待核实”，也不能用推算值包装成精确坐姿时长。因此当前页面显示保守状态，没有直接把恢复后的时间继续算成确定值。

### 6. Windows 相关功能不能仅凭 Mock 测试宣称完成

现有测试覆盖了消息契约、状态转换、提醒幂等、单实例和原生窗口烟测，但以下内容仍必须在目标 Windows 上实测：

- 系统通知是否被权限、专注助手或系统策略抑制；
- WTS 会话锁定 / 解锁通知的注册与注销；
- 休眠、唤醒和不同电源策略下的时间语义；
- 多显示器 DPI、读屏器和高对比度主题；
- PyInstaller 安装包启动、托盘和登录启动清理。

这也是为什么“系统通知样式预览”不等于“真实系统通知已交付”。

## 三、按阶段拆分的剩余工作

### Phase 4A：症状记录与安全规则基础（已完成）

已新增症状 migration、领域模型、service 和规则模块，接入保存 / 同日更新 / 编辑 / 删除 / CSV 导出，并补充 NULL / 0、日期校验、写失败、导出确认和警示规则测试。该阶段自动化测试覆盖 90/90；专业复核、真实 Windows 目标机验收和统计趋势不属于本阶段完成项。

### Phase 4B：专业确认训练与候选资料导入（基础已完成）

已建立候选 / 已确认 / 停用状态、来源和审核信息模型，允许用户录入专业确认但明确程序无法验证；已加入计划、训练日志、不适记录和只读日志历史展示。用户主动选择 `docs/yu_an_rehab_v1/catalogue.json` 后，10 项资料以 `CANDIDATE` 导入，重复导入按资料包 ID 跳过，非法结构在写库前拒绝，批量写入失败会回滚。初始计划仍为空，设计稿动作不能直接进入执行清单。剩余工作是训练提醒自动排程与更细的专业内容复核，不在本阶段擅自扩展。

### Phase 4C：统计趋势（已完成基础）

已从姿势事件和症状记录构造只读查询服务，接入 7 / 30 日范围、坐姿时长 / 症状变化 / 起身次数三个统计页签和首页今日摘要。已明确本地日期、跨午夜、未知区间、缺失值断点和事件重放规则；统计不自动声称病情好转，不用演示数据填充空白。医学趋势判断、备份恢复和真实目标机验收不属于本阶段。

### Phase 4D：设置与交互收口

提醒偏好、启动 / 恢复询问、人工姿势更正和本地数据管理已接入：设置页和提醒服务使用同一份 `SettingsService`；恢复会进入待确认，不静默继续计时；更正追加事件而不删除原始事实；备份使用 SQLite Backup API，恢复前执行 integrity / schema 校验，删除使用跨表事务并在提交后重载姿势状态；墙钟跳变会记录环境事实并进入待核实。声音偏好目前只保存配置，因为 Qt 托盘通知通道尚未提供静音参数，不能宣称已关闭系统通知声音。仍需真实 Windows 通知声音能力、文件锁和电源事件验收。

### Phase 5：可靠性专项

已完成基础故障注入：SQLite 启动前完整性检查、一致性备份 / 恢复、无效数据库保护、跨表删除事务回滚、重复启动锁、墙钟跳变检测、恢复刷新幂等和候选资料导入回滚均有自动化覆盖。新增真实临时磁盘 SQLite/WAL 文件测试：底层连接未调用正常收尾时重新打开数据库，姿势会进入待核实，原始坐下时间保留且不静默推算恢复期间时长。该测试是可控的异常退出模拟，不等同于真实进程崩溃、文件锁竞争或突然断电。姿势事件未变化但其他健康数据发生恢复时，数据管理服务会显式强制姿势进入待核实流程。仍需真实锁屏、睡眠、唤醒、通知抑制、DPI、无障碍，以及断电 / 崩溃现场验收。自动化通过不能替代这些实机测试。

### Phase 6：打包和目标机试用

已完成 PyInstaller EXE 与 Inno Setup 安装包的实际构建，以及冻结主窗口启动烟测；待完成主程序版本资源、安装 / 升级 / 卸载、登录启动清理，并在无 Python 环境的目标电脑上做实际试用。

## 四、必须优先修正或确认的问题

1. 应用组合根已把启动 / 恢复询问和人工更正接入主窗口；但真实锁屏、休眠、唤醒和断电后的现场交互仍需目标 Windows 验收。
2. 当前 `domain/posture.py` 的 `uncertain` 和 `NEEDS_CONFIRMATION` 是实现层简化表达，尚未完全呈现 PRD 三轴状态中的环境状态和可信度状态；后续若扩展恢复问询，应先冻结正式模型。
4. 用户明确要求每期分别汇报自动测试、模拟 Windows 事件、真实 Windows 集成和人工试用；当前不能把 100/100 自动化测试解释为真实 Windows 集成或 Phase 4–6 完成。

## 五、结论

未实现项主要集中在 Phase 4–6，不是 UI 遗漏。当前选择是：先把设计稿入口和页面结构做全，再按数据模型、服务契约、专业内容、真实 Windows 验收的顺序逐期接入。这样可以保证“页面看得到”与“业务真的可用”分开，避免出现假统计、未经确认的训练建议、静默恢复计时或虚假的测试结论。
