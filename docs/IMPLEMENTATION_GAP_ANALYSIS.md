# V1 未实现功能原因梳理

日期：2026-10-14

本文件回答一个问题：为什么设计稿里已经出现了很多入口，但对应业务仍显示“待实现”。结论先行：当前不是所有功能都没有做，而是 **Phase 1–3 的基础运行、姿势状态、提醒链路、Phase 4A 的症状记录基础和 Phase 4B 的专业确认训练基础已完成；Phase 4C–4D 的统计与交互收口，以及 Phase 5–6 的可靠性和安装交付仍未完成**。页面先补齐，是为了让产品结构完整，不把占位页冒充为可用功能。

## 一、当前已实现与未实现的边界

| PRD | 功能 | 当前状态 | 说明 |
| --- | --- | --- | --- |
| F01 | 开机启动、系统托盘、单实例、退出 / 暂停 | 部分已实现 | 当前用户登录启动、托盘菜单、单实例和退出确认已有；关闭窗口到托盘、安装后注册清理、目标机完整验收仍需补测 / 收口 |
| F02 | 35 分钟提醒 | 核心已实现 | 状态机生成一次性提醒事件，提醒投递有持久化和重试；真实 Windows 通知展示仍未完成实机验收，现有通知文案还有阈值条件问题 |

| F09 | 锁屏 / 休眠 / 崩溃 / 断电恢复 | 部分已实现 | 已有事件日志、启动中断标记和待核实姿势状态；未知区间的完整询问、时钟跳变、数据库备份恢复、断电故障注入和真实 Windows 验收尚未完成 |

## 二、为什么没有直接把占位按钮做成可用

### 1. 页面和业务数据不是同一件事

当前 SQLite schema 版本 5，已包含：

- `app_settings`
- `posture_events`
- `posture_snapshot`
- `environment_events`
- `reminder_deliveries`
- `symptom_entries`
- `exercises`
- `exercise_plans`
- `exercise_logs`

仍没有备份记录等表。统计不新增读取模型表，而是从既有姿势事件和症状记录只读推导；训练资料已经有正式数据契约，但没有内置任何真实动作资料。按照 PRD“不得伪造记录、统计”的要求，统计页只绘制本地已保存事实，缺失值保持为空，不使用演示数据。

### 2. 症状功能缺少完整契约，不只是几个输入框

F06 的统计契约已在 Phase 4C 实现并测试；仍需专业人员复核规则文案和后续医学产品边界：

- 每日记录的唯一性和可编辑规则；
- 疼痛 `NULL` 与 `0` 的存储和显示区别；
- 本地日期、UTC 时间、跨午夜的归属规则；
- 部位、腿部症状、活动关系的枚举或自由文本边界；
- 保存失败时的事务和界面反馈；
- CSV 导出范围、确认和隐私提示；
- 统计展示不应被解释为病情判断或医学趋势结论；
- 与异常症状提示共用的字段契约。

以上数据契约已在 Phase 4A / 4C 冻结并接入症状与统计 UI；医学文案复核、真实目标机验收和后续备份恢复仍不属于本阶段。

### 3. 康复训练不能用示例动作填充真实功能

PRD 明确要求：动作必须记录来源、内容、禁忌、审核人、专业确认时间和状态；未经专业确认不得加入执行计划；初始可执行计划必须为空。

当前没有医生或康复治疗师确认的内置动作资料，也没有可验证的专业资质系统。因此页面中的“猫牛式、桥式、腰部拉伸”仍只能作为设计稿位置占位；用户可以录入自己已有的专业资料，但程序只记录用户填写的确认信息，不验证资质，也不会自动推荐或排程。这个边界需要专业内容和数据契约，不是单纯开发一个按钮。

### 4. 异常症状提示必须先有医学复核后的规则和文案

PRD 要求使用固定、可测试的规则，不使用 LLM 推理，也不能把提示写成诊断结论。当前仍未完成：

- 警示字段和选项的专业复核；
- 会阴 / 肛周麻木、排尿排便改变、进行性腿无力等文案的专业复核；
- 就医紧迫性和“停止训练”的文案审查；
- 规则单元测试和误触发测试。

当前实现只执行固定规则并显示非诊断性提示，不推荐训练，也不替代医疗评估；发行前仍需完成专业复核和真实目标机验收。

### 5. 恢复功能不能只靠启动时重新开始计时

当前 `PostureService` 使用事件日志和快照恢复，并在发现上次运行未正常结束时进入待核实状态。这解决了“不要静默清零”的基础问题，但距离 F09 完整交付还差：

- 锁屏、睡眠、唤醒之间的真实 Windows 事件验收；
- 系统时间跳变和跨时区处理；
- 用户确认“中间一直坐着 / 中间起身 / 无法判断”的完整 UI；
- 用户追述时间的精度和证据标记；
- SQLite 完整性检查、备份、恢复和损坏处理；
- 崩溃、断电和重复启动故障注入。

恢复场景宁可保留“未知 / 待核实”，也不能用推算值包装成精确坐姿时长。因此当前页面显示保守状态，没有直接把恢复后的时间继续算成确定值。

### 6. Windows 相关功能不能仅凭 Mock 测试宣称完成

现有测试覆盖了消息契约、状态转换、提醒幂等、单实例和原生窗口烟测，但以下内容仍必须在目标 Windows 上实测：

- 系统通知是否被权限、专注助手或系统策略抑制；
- WTS 会话锁定 / 解锁通知的注册与注销；
- 休眠、唤醒和不同电源策略下的时间语义；
- 多显示器 DPI、读屏器和高对比度主题；
- PyInstaller 安装包启动、托盘和登录启动清理。

这也是为什么“系统通知样式预览”不等于“真实系统通知已交付”。

## 三、按阶段拆分的剩余工作

### Phase 4A：症状记录与安全规则基础（已完成）

已新增症状 migration、领域模型、service 和规则模块，接入保存 / 同日更新 / 编辑 / 删除 / CSV 导出，并补充 NULL / 0、日期校验、写失败、导出确认和警示规则测试。该阶段自动化测试覆盖 90/90；专业复核、真实 Windows 目标机验收和统计趋势不属于本阶段完成项。

### Phase 4B：专业确认训练（基础已完成）

已建立候选 / 已确认 / 停用状态、来源和审核信息模型，允许用户录入专业确认但明确程序无法验证；已加入计划、训练日志和不适记录。初始计划仍为空，设计稿动作不能直接进入执行清单。剩余工作是训练提醒自动排程、日志历史展示与更细的专业内容复核，不在本阶段擅自扩展。

### Phase 4C：统计趋势（已完成基础）

已从姿势事件和症状记录构造只读查询服务，接入 7 / 30 日范围、坐姿时长 / 症状变化 / 起身次数三个统计页签和首页今日摘要。已明确本地日期、跨午夜、未知区间、缺失值断点和事件重放规则；统计不自动声称病情好转，不用演示数据填充空白。医学趋势判断、备份恢复和真实目标机验收不属于本阶段。

### Phase 4D：设置与交互收口

提醒偏好基础已完成：设置页和提醒服务使用同一份 `SettingsService`，重复提醒开关会抑制 40 分钟后的后续投递，同时保留 35 分钟和 40 分钟首次提醒；设置可持久化并在重启后读取。声音偏好目前只保存配置，因为 Qt 托盘通知通道尚未提供静音参数，不能宣称已关闭系统通知声音。仍需完成启动 / 恢复询问、误操作更正 UI、备份 / 恢复 / 删除管理，以及真实 Windows 通知声音能力验收。

### Phase 5：可靠性专项

需要做数据库完整性检查、备份恢复、断电 / 崩溃 / 时钟跳变故障注入，以及真实锁屏、睡眠、唤醒、通知抑制、DPI 和无障碍验收。自动化通过不能替代这些实机测试。

### Phase 6：打包和目标机试用

需要完成 PyInstaller / Inno Setup 配置、资源和版本信息、安装 / 卸载、登录启动清理，并在无 Python 环境的目标电脑上做实际试用。

## 四、必须优先修正或确认的问题

1. `src/rehab_assistant/adapters/windows/notifications.py` 当前条件是 `threshold_minutes >= 2`。这会让 35 分钟提醒走 40 分钟文案。该文件是用户已有修改，本次没有擅自还原；下一阶段开始前必须确认这是否是临时调试改动。
2. 当前应用组合根把环境事件传给 `PostureService.observe_environment`，但没有完整的恢复询问 UI；因此测试能证明事件被记录，不能证明用户已完成恢复决策。
3. 当前 `domain/posture.py` 的 `uncertain` 和 `NEEDS_CONFIRMATION` 是实现层简化表达，尚未完全呈现 PRD 三轴状态中的环境状态和可信度状态；统计和恢复功能开始前应冻结正式模型。
4. 用户明确要求每期分别汇报自动测试、模拟 Windows 事件、真实 Windows 集成和人工试用；当前不能把 100/100 自动化测试解释为真实 Windows 集成或 Phase 4–6 完成。

## 五、结论

未实现项主要集中在 Phase 4–6，不是 UI 遗漏。当前选择是：先把设计稿入口和页面结构做全，再按数据模型、服务契约、专业内容、真实 Windows 验收的顺序逐期接入。这样可以保证“页面看得到”与“业务真的可用”分开，避免出现假统计、未经确认的训练建议、静默恢复计时或虚假的测试结论。
